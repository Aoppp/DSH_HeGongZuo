# “和工作”基于 DSH 的技术路线

## 1. 产品定位

“和工作”将以 DSH 作为 Agent 运行框架，最终呈现为面向企业管理人员的 Web 工作台。用户通过自然语言提出员工管理任务，系统在对话中调用受权限控制的业务工具，并用结构化界面展示员工、审批、执行过程和结果。

第一阶段只开发一个“员工管理 Agent”。它成熟之前，不并行开发其他子 Agent。

## 2. 总体原则

1. **DSH 运行时优先**：复用 DSH 的会话、模型调用、工具注册、Agent 循环与事件流；用户界面由“和工作”原生实现。
2. **插件式扩展**：员工管理能力作为独立插件或包接入，不直接修改 DSH 内核。
3. **业务与框架隔离**：员工数据、权限、审批和审计属于“和工作”业务层；推理循环属于 DSH。
4. **先 Mock 后正式**：先用可控的 Mock 数据完成闭环，接口稳定后替换为数据库及正式企业系统。
5. **高风险操作可控**：查询可以直接执行；新增、修改、离职等操作必须经过权限校验、预览确认与审计记录。
6. **版本可复现**：DSH、pnpm 和运行时版本都必须锁定，升级通过单独任务验证。

## 3. 分阶段交付

### Phase 0：DSH 基础环境

- 初始化 Git 项目和 pnpm workspace。
- 锁定 Node.js、pnpm 与 DSH 版本。
- 提供环境变量模板和环境检查脚本。
- 验证 DSH CLI 与 Web UI 能正常启动。
- 记录技术路线和开发日志。

完成标准：新开发者按 README 安装依赖后，可以启动 DSH Web；仓库不包含真实密钥。

### Phase 1：员工管理 Agent 设计

- 定义用户角色、权限边界和首批场景。
- 定义员工领域模型和工具契约。
- 明确查询、变更、审批、审计四类流程。
- 建立测试用例与验收标准。

首批建议场景：员工查询、组织信息查询、新员工入职草稿、员工信息变更草稿和离职流程草稿。

### Phase 2：Mock 员工管理闭环

- 建立独立员工管理插件包。
- 接入 DSH 工具注册和事件机制。
- 使用本地 Mock 数据实现查询与变更预览。
- 增加确认、权限检查和操作审计。
- 在“和工作”原生 Agent 界面中展示业务结果和工具状态。

### 当前插入里程碑：“和工作”平台视觉原型

- 在 `apps/web` 建立独立的 React 平台外壳，不修改或复制 DSH Web 源码。
- 将平台功能、导航、角色访问范围和样式拆分为可独立增删的模块。
- 当前只开放老板和开发者两种预览角色，老板代表企业所有者和最高业务权限。
- 只保留概览、员工管理 Agent 和开发控制台；消息、项目、任务、文档、日程等未开发模块已从代码与导航删除。
- “和助手”是平台侧 Agent 品牌；员工 Agent 使用原生会话界面，通过 DSH HTTP/WebSocket API 访问底层运行时，不渲染 DSH Web 的品牌与工作区页面。
- 平台按账号自动创建并注册专属 Workspace，用户不接触文件路径；Workspace、会话和业务数据库保持不同职责。
- 增加老板专属“管理驾驶舱”，用独立 Mock 数据模型验证员工、项目、销售、财务、审批指标汇总、趋势、异常和 AI 分析的产品形态。
- 用账号记录自动映射老板或开发者角色，删除登录页身份选择和登录后角色切换；当前为本地测试账号，仍需在正式数据层阶段接入服务端认证。

### Phase 3：质量与安全

- 为工具契约、权限规则和关键流程增加自动化测试。
- 增加提示注入、越权、重复提交和数据泄露测试。
- 建立日志脱敏、可观测性和失败恢复机制。
- 通过固定任务集评估 Agent 的正确率和可控性。

### Phase 4：正式数据层

- 把 Mock 仓储替换为正式数据库适配器。
- 接入统一身份认证和基于角色的权限系统。
- 根据需要连接 HR、OA、通讯录等企业系统。
- 进行数据迁移、灰度验证和回滚演练。

业务工具契约应保持稳定，使 Agent 不需要因为数据源变化而重写。

### Phase 5：产品化

- 完善“和工作”品牌、导航和员工管理工作台。
- 增加管理员配置、使用反馈、运营指标和告警。
- 完成部署、备份、灾备及企业安全审查。

### Phase 6：扩展其他 Agent

只有员工管理 Agent 达到正式上线标准后，才评估新的子 Agent。新的 Agent 继续复用统一的身份、权限、审批、审计和 UI 基础设施。

## 4. 预期目录演进

```text
DSH和工作/
├── docs/                       # 架构、需求、接口和决策文档
├── packages/
│   ├── employee-agent/         # 员工管理 Agent 与提示配置
│   ├── employee-domain/        # 领域模型、工具契约与规则
│   ├── employee-mock-adapter/  # Phase 2 的 Mock 数据适配器
│   └── shared/                 # 少量跨包公共类型和工具
├── scripts/                    # 项目环境与维护脚本
├── .env.example
├── package.json
└── pnpm-workspace.yaml
```

上述业务包将在对应阶段按需建立。本阶段不创建空业务实现，避免提前固定尚未评审的边界。

## 5. 当前明确不做的内容

- 不自研 Agent 推理框架。
- 不维护 DSH 的私有分叉。
- 不同时开发多个业务 Agent。
- 不在 Phase 0 接入正式员工数据。
- 不把真实 API 密钥、员工隐私数据或生产配置提交到 Git。

## 6. 当前进度与下一步

- Phase 0 已完成：DSH 环境、pnpm workspace、TypeScript 基线和 Web 启动验证均已通过。
- Phase 1 已完成：角色权限、员工领域模型、工具契约、Mock 数据规则和验收标准已经形成文档及代码。
- Phase 2 的只读里程碑已完成：员工管理 DSH bundle、Mock 仓储和三个只读工具已经实现并安装到本地 Web profile。
- 已完成“和工作”原生员工 Agent 界面的第一版接线：会话列表、历史记录、流式事件、工具状态、输入和账号 Workspace 自动绑定均已连接 DSH。
- 下一步仍只完善员工管理 Agent，不增加其他业务 Agent；优先补齐审批/提问交互、服务端认证代理和正式数据权限。
