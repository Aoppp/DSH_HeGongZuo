# 员工管理 Agent 产品与技术规格（Phase 1）

## 1. 本阶段目标

本阶段固定员工管理 Agent 的业务边界、数据契约和安全规则，为下一阶段接入 DSH 工具提供依据。当前交付的数据全部为虚构测试数据，不连接真实员工系统，不允许 Agent 直接执行不可逆的人事操作。

## 2. 首批用户场景

1. 按姓名、工号、部门、岗位、状态或工作地点查询员工。
2. 查看某位员工的工作信息和直属经理。
3. 查看部门成员与汇报关系。
4. 创建入职方案草稿，但不直接创建正式员工。
5. 创建调岗、修改直属经理或状态变更草稿。
6. 创建离职流程草稿，但不直接停用账号或删除员工。
7. 查看操作预览、审批状态和审计记录。

员工身份证、银行卡、居住与身份证地址由平台存储，但仅用于人事档案管理：前端默认脱敏展示（点击可查看原文），Agent 工具字段白名单不返回这四类字段。工资、医疗信息和绩效敏感信息仍不属于平台存储范围。

### 2.1 敏感数据政策

- 敏感字段：身份证/护照号（`idNumber`）、银行卡号（`bankAccount`）、居住住址（`residentialAddress`）、身份证地址（`idAddress`）。
- 存储边界：平台 PostgreSQL 存储以上四类字段，用于完整人事档案；不存储薪酬、医疗或健康信息。
- Agent 边界：`employee_search`、`employee_get`、`organization_list_members` 的输出字段投影白名单不包含任何敏感字段，模型无法通过工具获得原文。
- 前端边界：员工档案详情默认脱敏（如 `3411**********5817`），点击眼睛图标显示原文；脱敏是界面层措施，API 仍返回全量字段，正式部署前必须接入服务端权限校验与字段过滤。
- 数据文件：`data/` 下的员工 Excel 及导入问题清单包含真实个人信息，已加入 Git 忽略，禁止提交仓库。

## 3. 用户角色与权限

| 角色 | 查询基础员工信息 | 查询本部门 | 创建变更草稿 | 审批变更 | 执行变更 | 查看审计 |
| --- | --- | --- | --- | --- | --- | --- |
| 普通员工 | 仅本人及公开通讯录字段 | 否 | 仅本人允许的申请 | 否 | 否 | 仅本人申请 |
| 部门经理 | 本部门必要字段 | 是 | 本部门 | 部分 | 否 | 本部门相关 |
| HR 专员 | 授权范围 | 是 | 是 | 部分 | 否 | 授权范围 |
| HR 管理员 | 是 | 是 | 是 | 是 | 经确认后执行 | 是 |
| 审计员 | 只读 | 只读 | 否 | 否 | 否 | 是 |
| 系统管理员 | 系统配置所需 | 否 | 否 | 否 | 否 | 技术审计 |

系统管理员不因维护系统而自动获得完整人事数据权限。Phase 2 在没有真实身份系统时，将使用显式测试角色，默认权限应为最低权限。

## 4. 员工领域模型

员工记录当前包含以下字段：

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `id` | 系统稳定主键 | 不随工号或邮箱变化 |
| `employeeNo` | 企业工号 | 全局唯一 |
| `displayName` | 工作显示名称 | 非空 |
| `workEmail` | 工作邮箱 | 全局唯一 |
| `workPhone` | 工作电话 | 测试数据必须明显虚构 |
| `departmentCode` | 部门稳定编码 | 用于系统关联 |
| `departmentName` | 部门显示名称 | 用于界面展示 |
| `jobTitle` | 岗位名称 | 非空 |
| `managerId` | 直属经理员工 ID | 可为空，不允许循环汇报 |
| `employmentType` | 用工类型 | 全职、兼职、外包或实习 |
| `status` | 在职状态 | 试用、在职、休假或非活跃 |
| `hireDate` | 入职日期 | ISO 日期 `YYYY-MM-DD` |
| `workLocation` | 工作地点 | 当前为城市级信息 |

TypeScript 类型位于 `packages/employee-domain/src/index.ts`，机器可读的 JSON Schema 位于 `packages/employee-domain/schemas/employee-dataset.schema.json`。

## 5. DSH 工具契约

文档使用 `employee.search` 这类点号名称表达业务命名空间；实际注册到模型的 DSH 工具使用兼容主流模型 API 的下划线名称：`employee_search`、`employee_get`、`organization_list_members`。两者语义一一对应。

### 5.1 只读工具

#### `employee.search`

运行时名称：`employee_search`。

- 输入：可选的关键词、部门、岗位、状态、地点、分页参数。
- 输出：脱敏后的员工摘要列表、命中总数和分页信息。
- 权限：根据调用者角色自动增加数据范围过滤，模型不能绕过。

#### `employee.get`

运行时名称：`employee_get`。

- 输入：员工 `id` 或精确工号。
- 输出：调用者有权查看的员工字段。
- 权限：字段级和记录级过滤必须在工具内部完成。

#### `organization.list_members`

运行时名称：`organization_list_members`。

- 输入：部门编码，可选是否包含下级部门。
- 输出：部门信息、成员摘要和汇报关系。

#### `audit.search`

- 输入：时间范围、操作人、对象、动作类型和分页参数。
- 输出：只读审计记录。
- 权限：仅授权角色可用。

### 5.2 草稿工具

#### `onboarding.create_draft`

- 输入：候选员工的必要工作信息、计划入职日期、部门和经理。
- 输出：草稿 ID、缺失字段、风险提示和预览。
- 不产生正式员工记录。

#### `employee_change.create_draft`

- 输入：员工 ID、拟变更字段、变更原因和生效日期。
- 输出：变更前后对比、审批要求、草稿 ID。

#### `offboarding.create_draft`

- 输入：员工 ID、计划离职日期、原因分类和交接负责人。
- 输出：离职检查清单、影响系统、审批要求和草稿 ID。
- 原因的自由文本应限制可见范围，不能进入普通对话摘要。

### 5.3 提交工具（后续阶段）

#### `change.commit`

只有正式身份、权限和审批能力就绪后才能启用。调用必须同时满足：

1. 使用已存在且未过期的草稿 ID。
2. 服务端重新计算变更内容，不能信任模型传入的预览。
3. 调用者具备执行权限。
4. 所需审批已经通过。
5. 用户在本次会话中完成明确确认。
6. 使用幂等键防止重复提交。
7. 写入不可删除的审计记录。

Phase 2 默认不提供真实 `change.commit`，只模拟提交结果。

## 6. 统一响应结构

所有业务工具应返回结构化结果，最少包含：

```ts
interface ToolResult<T> {
  ok: boolean
  data?: T
  error?: {
    code: string
    message: string
    retryable: boolean
  }
  audit: {
    traceId: string
    action: string
    actorId: string
    occurredAt: string
  }
}
```

面向用户的自然语言解释由 Agent 生成，但权限判断、数据过滤、确认状态和审计字段必须由业务工具确定。

## 7. 变更流程

```text
用户提出请求
  → Agent 收集必要信息
  → 工具执行权限检查
  → 创建草稿并返回变更预览
  → 用户明确确认
  → 审批（如果需要）
  → 服务端重新校验
  → 模拟或正式提交
  → 返回结果并记录审计
```

任何一步失败都不能静默跳过。用户修改字段后，旧确认自动失效，必须重新展示预览。

## 8. Mock 数据策略

- 当前固定提供 10 名虚构员工，覆盖 6 个部门、3 种员工状态和两级以上汇报关系。
- 邮箱统一使用保留测试域名 `example.com`。
- 电话使用明显无效的 `+86-000-...` 格式。
- 数据文件明确标记 `synthetic-non-personal`。
- 通过 `pnpm validate:data` 检查数量、必填字段、唯一性、枚举值、经理引用和循环汇报。
- 正式数据已导入：`apps/api/scripts/import-employees.mjs` 从 `data/王叔和在职.xlsx` 全量替换导入 82 名在职员工（`pnpm db:seed` 默认 dry-run，`--apply` 清空后导入），导入时原样保留数据并生成问题清单 `data/import-issues.md`；原始 Excel 与问题清单位于 `data/`，已加入 Git 忽略。

## 9. Phase 2 验收标准

1. 用户能在 DSH Web 中查询 10 名虚构员工。
2. 姓名、工号、部门、状态和地点筛选结果正确。
3. 无权限角色无法获得受限记录或字段。
4. Agent 能创建入职、员工变更和离职草稿。
5. 所有变更都先展示差异，未经确认不得模拟提交。
6. 重复提交相同幂等键只产生一次结果。
7. 每次工具调用都有 trace ID 和审计记录。
8. 测试数据、构建、类型检查和自动化测试全部通过。

## 10. 暂不实现

- 不连接真实 HR、OA、考勤或通讯录系统。
- 不存储薪酬、医疗或健康信息；身份证、银行卡、居住住址与身份证地址由平台存储，但 Agent 工具不返回、前端默认脱敏（见 2.1 敏感数据政策）。
- 不启用不可逆的正式员工变更。
- 不开发第二个业务 Agent。
